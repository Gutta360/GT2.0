# PostgreSQL schema

Flyway migration `V1__create_gt2_backup_schema.sql` owns the schema. Hibernate is configured as `validate`; it does not create or update production tables.

| Table | Purpose | Important constraints |
|---|---|---|
| `tenants` | Isolation and lifecycle root | unique tenant code; active/suspended check |
| `enrollment_codes` | One-use device bootstrap | unique SHA-256 digest, expiry, consumption time |
| `devices` | Registered tablet identity | unique token digest; tenant FK; active/revoked check |
| `patients` | Latest uploaded patient state | tenant/number and normalized tenant/name/mobile uniqueness; domain checks; positive record version |
| `sync_batches` | Idempotent request envelope | batch UUID and request hash; counts/completion |
| `processed_sync_events` | Durable idempotency/history | unique tenant/event and tenant/entity/version; JSONB payload |
| `sync_event_results` | Ordered explicit acknowledgments | unique batch/event; constrained result status |
| `backup_snapshots` | Encrypted file metadata | tenant/device FKs, SHA-256, size, schema/contract versions, availability |
| `recovery_audit` | Download/restore audit | tenant/device/snapshot, action, outcome, timestamp |

All timestamps are `TIMESTAMPTZ` and the JVM/JDBC session uses UTC. Monetary patient input is stored as integer cents. UUIDs are generated by the application. Tenant-scoped repository methods are used for all device-facing reads.

## Migration procedure

1. Back up PostgreSQL.
2. Deploy a tested JAR containing only forward migrations.
3. Start one application instance; Flyway obtains its migration lock and applies changes.
4. Verify `/actuator/health`, `flyway_schema_history`, and application logs.
5. Never edit an already-applied migration. Add `V2__...sql` and later migrations.

The real-PostgreSQL Testcontainers suite is the schema/constraint gate. It is skipped, and therefore not a passing gate, when no container runtime is available.
